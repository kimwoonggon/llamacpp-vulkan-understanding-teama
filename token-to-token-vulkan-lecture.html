가중치의 이름과 자리를 정한다

이번 실행에서 로더는 GGUF 파일 전체를 CPU 주소 공간에 한 번 매핑하고 GPU 모델 버퍼를 미리 확보합니다. GPU 전송의 반복 단위는 가중치 텐서 하나입니다. load_all_data의 1625행은 for (struct ggml_tensor * cur : tensors)입니다. 예를 들어 0번 층의 Wq 차례에는 Wq의 4.5 MiB만 파일 매핑 → staging → GPU의 Wq 자리로 옮기고 복사가 끝나면 다음 텐서로 넘어갑니다. K와 V도 각각 따로 옮깁니다. Windows에서 이번 GGUF의 크기는 3,560,416,288바이트(3.32 GiB)입니다. 590행에서 파일 전체를 매핑하고, 614행에서 같은 시작 주소와 전체 길이로 PrefetchVirtualMemory를 호출했습니다(디버거에서 범위 1개, 반환값 1 확인). Windows가 파일 페이지를 RAM에 미리 준비하도록 요청한 것입니다. 디스크에서 새로 읽은 양과 그 순간 RAM에 상주한 양은 이 호출값만으로 알 수 없습니다. 로더는 별도 CPU 배열에 모델 전체를 복사하지 않습니다.

Wq의 한 행이 GPU에서 Q 한 값이 되기까지

Wq의 0번 행과 입력 X의 내적에 bias[0]을 더하면 Q[0]이 나옵니다. 1번 행도 같은 X와 곱하고 bias[1]을 더합니다. 한 그룹은 두 행을 맡고, 그룹 안의 스레드들은 각 행의 열을 나눠 계산합니다.

마지막 셰이더의 출력 버퍼를 CPU에서 읽는다

‘ Paris’ 뒤에 올 토큰을 고르려면 후보마다 점수가 하나씩 필요합니다. GPU가 만든 점수표가 어떻게 CPU의 float *logits까지 오는지, 마침표 후보인 ID 13을 따라가 봅니다.

그중 logits[13] 하나는 어디로 가나?

디버거에서 요청의 offset은 0인데 GPU 복사 명령의 srcOffset은 159,744였습니다. 0은 텐서의 첫 바이트이고, 그 첫 바이트가 GPU 버퍼 안에서는 +159,744 B에 있습니다. 버퍼 핸들은 버퍼를 지정하고 오프셋은 그 안의 위치를 지정합니다.

별도 staging과 CPU의 memcpy는 언제 필요한가?

이 비동기 읽기 경로에서는 ggml_vk_host_get이 CPU 목적지에 대응하는 Vulkan 버퍼를 찾으면 그 버퍼를 staging으로 씁니다. 찾지 못하면 읽기 함수가 false를 반환하고, 호출자가 별도 staging을 확보합니다. GPU가 거기에 복사하고 완료를 기다린 후 CPU가 staging → 요청한 주소로 memcpy합니다. ggml-vulkan.cpp 12972–13000행, 13143–13146행.

CPU는 언제 이 점수를 읽어도 될까?

  1. CPU · 복사 명령 기록get_async가 읽기를 요청합니다. Vulkan은 barrier와 copyBuffer를 명령 버퍼에 기록합니다. 이때 CPU 포인터는 이미 있습니다.
  2. 큐 제출 → GPU 복사 실행샘플러가 동기화를 요청하면 CPU는 남은 명령을 큐에 제출합니다. 배리어가 앞선 셰이더의 쓰기와 뒤따르는 복사 읽기를 연결합니다. GPU가 완성된 점수표를 호스트 출력 버퍼로 한 번 복사합니다.
  3. CPU · fence 완료 확인 후 읽기복사가 끝나면 GPU의 완료 신호가 켜집니다. CPU는 fence 대기에서 돌아와 매핑된 주소를 사용합니다. 이제 logits[13]을 읽어 다른 후보들의 점수와 비교할 수 있습니다.
